# 대화 기록 안정성 · 불러오기 속도 — 원인 정리 · 시험 순서

2026-11-23 정리. 회사판 Coris(PostgreSQL 저장)에서 생기는 문제를 로컬 참조본 구조와 비교해 원인 후보와 시험 순서를 정리한다.

## 1. 증상 (회사판)

- 대화창을 오가면 로그(tool 처리 과정) · 답변 이력이 사라지거나 잘 안 보인다
- 이어서 물으면 앞 내용을 몰라 하나씩 다시 알려줘야 한다 → 대화가 길어지고 무거워진다
- 2026-11-23 수정: 대화를 열 때 **DB 에서 다시 불러와 화면에 그리도록** 바꿨다 → **속도 · 안정성이 너무 느림**
- **답변 중인 대화를 눌러도 동작하지 않는다**

## 2. 회사판 확인 결과

| 항목 | 회사판 | 판단 |
|---|---|---|
| 서버 수 | dev 1개 · prd 2개 | dev(1개)에서도 같은 증상 → **서버 여러 개는 주원인 아님** (prd 에서 증상을 키울 수는 있음) |
| 질문 저장 시점 | 질문이 들어오면 바로 저장 | 좋음. 단 답변 저장 시점 · 질문 이중 저장 여부 확인 필요 |
| 대화 다시 열기 | DB 에서 다시 읽음 | 좋음. 단 읽는 양 · 횟수가 느린 원인일 수 있음 |
| 이전 tool 결과 연결 | `message_id` 로 (session_id 아님) | 구조는 맞음. 단 화면이 서버 `message_id` 를 아는지 확인 필요 |

## 3. 저장소 차이 — PostgreSQL 자체는 문제가 아니다

| | 로컬 (`backend/data/hub.json`) | 회사 (PostgreSQL) |
|---|---|---|
| 동시 사용 | 서버 프로세스 1개에서만 안전 | 여러 서버가 함께 써도 안전 |
| 저장 | 저장마다 파일 전체를 다시 씀 (지금 한 턴 약 8ms) | 바뀐 행만 |
| 용도 | 개발 · 시험 | 운영 |

문제는 저장소가 아니라 **저장소를 둘러싼 동작 방식**(답변 생성이 화면 연결에 묶였는지, 무엇을 얼마나 불러오는지)이다.

## 4. 원인 후보

### ① 답변 생성이 화면 연결에 묶여 있음 — 가장 유력
- 로컬은 답변을 **백그라운드 작업**(`backend/hub/runs.py`)으로 돌린다 — 화면이 다른 대화로 가도 서버가 끝까지 만들어 저장하고, 돌아오면 이어서 보여준다
- 회사판에 이 분리가 없으면 대화를 옮기는 순간 연결이 끊기며 답변 생성도 취소된다. 저장이 "정상 종료일 때만" 이면 질문만 남고 **답변 · tool 기록이 사라진다**
- 그래서 화면에서 **답변 중에는 대화 전환을 막아 둔** 것으로 보인다 → "답변 중인 대화를 눌러도 동작 안 함" 과 같은 뿌리

### ② 새 답변에 서버 `message_id` 가 없음
- 로컬 화면은 방금 받은 답변에 화면 임시 id(`localId()`)를 붙이고, 서버 id 는 대화를 다시 불러와야 생긴다
- 회사판도 같다면: 같은 대화에서 바로 이어 물을 때 직전 답변의 tool 결과를 못 찾는다 → 다시 조회 · 다시 질문. 새로고침 후에는 되기도 한다 (되다 안 되다)

### ③ 대화를 연 직후 기록이 다 불러와지기 전에 질문이 나감
- 화면이 기록을 비우고 DB 에서 다시 불러오는 사이에 질문을 보내면 빈 기록으로 나간다 → LLM 이 앞 내용을 모름

### ④ 불러오기가 무거움 (오늘 수정 후 느려진 원인 후보)
- tool 원본 결과 · trace · 이벤트까지 **전부** 화면에 내려보냄 — 로컬은 trace 를 빼고 화면용 요약만 보낸다 (`backend/routers/hub.py` `get_conversation`)
- 메시지마다 tool · 이벤트를 따로 조회 (쿼리 수십 번), 인덱스 없음, async 안의 동기 DB 드라이버
- 이벤트마다 · 답변이 끝날 때마다 전체를 다시 조회, 또는 폴링
- 응답은 빨리 왔는데 모든 메시지의 마크다운 · 차트를 한꺼번에 그리느라 화면이 멈춤

## 5. 내일 시험 순서

### 시험 1 — 대화 불러오기가 어디서 느린가 (④)
브라우저 개발자 도구 → Network → 대화를 클릭할 때의 조회 요청

| 보이는 것 | 의미 | 볼 곳 |
|---|---|---|
| Waiting(TTFB) 이 김 | 서버 · DB | 쿼리 수 · 인덱스 · 동기 드라이버 · 원본 결과까지 조회하는지 |
| 응답 크기가 큼 (수백 KB 이상) | 너무 많이 보냄 | tool 원본 결과 · trace · 이벤트를 화면에 보내는지 |
| 응답은 빠른데 화면이 멈춤 | 그리기 | Performance 탭 · 화면 probe 의 longtask ([TIMING.md](TIMING.md)) |
| 같은 조회가 여러 번 | 반복 조회 | 이벤트 · 답변 끝 · 폴링마다 다시 부르는지 |

기록할 것: Waiting 시간 · 응답 크기 · 요청 횟수 (짧은 대화 / 긴 대화 각각)

### 시험 2 — 답변이 화면 연결에 묶여 있는가 (①)
1. 질문을 보내고 답변 중에 **새로고침**(또는 탭 닫기)
2. 서버 로그에 취소(CancelledError) · 연결 끊김이 찍히는지
3. 1~2분 뒤 그 대화를 다시 열어 답변이 **완성돼 있는지 / 질문만 있는지 / 중간에 끊겨 있는지**
→ 질문만 있거나 끊겨 있으면 ①

### 시험 3 — 이어 묻기에서 앞 결과를 찾는가 (② · ③)
1. tool 을 쓰는 질문 → 답변 → **새로고침 없이** 바로 후속 질문 ("그중 두 번째만 다시 보여줘" 처럼 앞 결과가 필요한 것)
2. 같은 걸 **새로고침 후** 후속 질문
3. Network 에서 후속 질문 요청 본문에 이전 답변의 서버 `message_id` 가 있는지
4. 대화를 연 **직후 바로** 질문 vs **잠시 뒤** 질문
→ 1 만 실패하면 ② · 4 의 바로 질문만 실패하면 ③.
측정 코드를 붙였다면 첫 agent LLM 호출의 `msgs`(LLM 에 실제로 들어간 메시지 수)로 확인 ([TIMING.md](TIMING.md))

### 시험 4 — DB 상태 (② · 질문 이중 저장)
3턴 대화 후 DB 에서 그 대화 조회
- 질문이 두 번씩 들어가 있지 않은지 (질문 즉시 저장 + 끝날 때 질문·답변 함께 저장)
- 답변 · tool 결과가 턴(`message_id`)마다 따로 있는지

## 6. 고치는 방향 (원인 확정 후)

### 불러오기 (④)
| 항목 | 방법 |
|---|---|
| 내려보낼 것 | 메시지 본문 + tool 카드 요약(이름 · 시간 · 성공 여부)만. 원본 결과는 카드를 펼칠 때 따로 |
| 쿼리 | 메시지 1번 + tool 요약 1번(`WHERE message_id IN (...)`) — 메시지마다 조회하지 않기 |
| 인덱스 | `(conversation_id, created_at)`, `(message_id)` |
| 양 | 최근 N턴, 위로 올리면 "이전 대화 더 보기" |
| 시점 | 대화를 클릭할 때 한 번. 답변 중에는 다시 조회하지 않기 |
| 서버 | async 드라이버 + 연결 풀 |

### 답변 중 대화 열기 (①)
답변 생성을 화면 연결에서 떼어 낸다 (백그라운드 작업). 그 위에서 두 가지 중 선택:

| 방법 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **B. DB 상태 확인 (먼저 권장)** | 돌아오면 DB 의 질문 + "답변 중" 표시, 몇 초마다 상태만 확인 → 완료되면 답변 표시 | 서버 여러 대에서도 단순 · 안정 | 돌아온 뒤엔 글자가 실시간으로 흐르지 않음 (답변 중간 저장으로 보완) |
| A. 진행 중 스트림에 다시 붙기 (로컬 방식) | 돌아오면 진행 중인 스트림에 이어 붙음 | 실시간으로 이어 보임 | prd 2대면 같은 서버로 가야 함 (sticky session) 또는 이벤트를 Redis · DB 에 |

### 기록 연결 (② · ③)
- 답변이 끝나면 서버가 **`message_id` 를 화면에 보낸다** (완료 이벤트에 포함) → 화면은 임시 id 를 서버 id 로 바꾼다
- 기록의 기준은 DB 하나 — 화면은 대화 id + 새 질문만 보내고 서버가 DB 에서 기록을 불러오는 쪽이 안전 (③ 이 원천적으로 사라짐)
- 질문 이중 저장 제거, 메시지마다 상태 칸(답변 중 / 완료 / 중지)

## 7. 결과를 가져오면

시험 1 의 숫자(Waiting · 크기 · 횟수)와 시험 2~4 결과를 가져오면 원인을 확정하고, 회사판 구조에 맞춘 수정 코드를 정리한다.
로컬 참조본에 B 방식(DB 상태 확인)과 가벼운 대화 조회 API 를 먼저 만들어 두는 것도 가능하다.
