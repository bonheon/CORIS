# Agent 응답 속도 — 검토 · 적용 · 남은 작업

2026-11-23 정리. 회사판 Coris 에서 tool 이 많아지며 **ReAct 순환이 반복되고 답변이 오래 걸리는 문제**, **화면이 실시간으로 안 나오는 문제**를 다룬다.
로컬 참조본에 먼저 넣고, 회사판에서 측정 → 적용 여부를 정한다.

## 1. 왜 느린가 (ReAct 구조)

- LLM 호출 수 = tool 호출 수 + 1. tool 을 차례로 3개 부르면 LLM 을 4번 부른다
- 부를 때마다 tool 정의 · 시스템 프롬프트 · tool 안내 · 지금까지의 결과를 **처음부터 다시** 보낸다 — tool 이 많을수록 무겁다
- tool 이 비슷하거나 결과 · 오류가 애매하면 같은 조회를 반복한다 (15개 넘으면 선택 정확도 저하 — `routing.py` MAX_TOOLS)

## 2. 이번에 적용한 것 (로컬)

| # | 내용 | 위치 | 설정 |
|---|---|---|---|
| 2 | **반복 호출 차단** — 같은 질문 안에서 같은 tool · 같은 인자는 실행하지 않고 "앞 결과를 쓰라" 안내. 같은 응답 안 중복도 한 번만. 오류 난 호출은 1번 재시도 허용. 반복만 한 라운드가 2번이면 바로 정리. 이전 질문의 조회는 세지 않음 | `agent.py` `_make_tools_node` | `AGENT_DUP_ERROR_RETRY=1` · `AGENT_DUP_WRAP_ROUNDS=2` · `AGENT_DUP_EXCLUDE=` |

로컬 확인 (가짜 LLM · 가짜 tool): 한 응답에 A·B·A → A·B 만 동시 실행(0.5초 tool 2개에 0.51초) · 반복 2라운드 후 정리 · 오류 tool 3번 중 2번만 실행 · `run_python` 같은 코드 3번 모두 실행 · 화면 이벤트는 실제 실행한 tool 만.
실제 LLM 을 붙인 측정은 회사에서 처음.

## 3. 회사판 적용 순서 (결정)

1. **측정 코드 먼저** 넣고 지금 상태를 잰다 ([TIMING.md](TIMING.md) 3절)
2. **2번 · 3번**(+ 7②) 적용 후 같은 질문으로 다시 잰다 → 효과 비교
3. 결과를 보고 하이브리드(아래 5절) 적용 여부를 정한다

옮길 때 확인할 것
- 사내 게이트웨이 · 모델이 **한 응답에 tool 호출 여러 개**를 내는지 — 안 되면 3번은 효과 없음
- 게이트웨이의 **프롬프트 캐시**(vLLM `--enable-prefix-caching` 등) — 꺼져 있으면 7② 효과 없음
- 같은 인자로 다시 불러야 하는 tool(실시간 상태 조회 등) → `AGENT_DUP_EXCLUDE`
- PostgreSQL 저장 호출을 `db.*` 구간으로 감싸기 — 특히 이벤트마다 저장하는지, async 안의 동기 드라이버인지 (서버 멈춤의 흔한 원인)

## 5. 하이브리드 (계획 먼저 + 단계 안에서만 ReAct) — 검토만, 미적용

요즘 흐름은 ReAct 단독보다 **큰 계획을 먼저 세우고, 결과를 봐야 다음이 정해지는 부분만 ReAct** 로 두는 방식이다.
Coris 에는 계획을 실행할 엔진(`hub/steps.py` — tool 실행 · `{{s1.rows}}` 참조 · `for_each` 동시 실행 · 조건 · 판단 · 보고 · `validate()`)이 이미 있어, **질문마다 임시 단계형 skill 을 만드는 planner** 가 핵심 추가분이다.

```
질문 → Router (기존 호출에 mode 칸 추가: direct | plan)
  ├ 등록된 단계형 skill → steps.py              (지금과 같음)
  ├ direct (단순 조회 1~2개) → 지금의 ReAct     (계획 비용 없음)
  └ plan (여러 단계 · 연쇄 · 항목별 반복)
       ① Planner (LLM 1회) — submit_plan tool 로 단계 목록 제출 (structured output 대신 function calling)
       ② validate() → 실패하면 ReAct 로
       ③ steps.py 실행 — 정해진 조회는 LLM 없이, 독립 단계는 동시에
          └ explore 단계만: 그 단계의 tool 만 붙인 짧은 ReAct (최대 2~3회)
       ④ 실패 · 빈 결과 → 계획 다시 1번만
       ⑤ 보고 (LLM 1회, 스트리밍)
```

| 질문 유형 | 지금 | 하이브리드 |
|---|---|---|
| 단순 조회 1~2개 | LLM 2~3회 | 같음 (direct) |
| 독립 조회 여러 개 | LLM 2회 (3번 적용 후) | 비슷 |
| 연쇄 + 항목별 반복 (Hold Lot → Lot 마다 설비 효율 → …) | LLM 5~9회 | **LLM 2~3회** |

근거: 같은 Hold 보고 — 단계형 5~6초 vs 프롬프트형 9초.

새로 만들 것: planner(`submit_plan`) · `explore` 단계 · 독립 단계 동시 실행(지금 엔진은 단계를 차례로, 동시 실행은 `for_each` 안에서만) · 다시 계획 1회 · 단계 8개 상한.
저장: 기존 테이블 그대로 — 단계 엔진이 ReAct 와 같은 이벤트(`tool_start` · `tool_end` · `delta`)와 trace 형식을 낸다. 계획 JSON 은 assistant 메시지의 JSON 칸에. 기록만 하는 모드의 분석에는 `plan_logs` 테이블이 있으면 편하다(선택).

위험: 사내 모델의 계획 품질(참조 문법 오류 → 예시 계획 · 검사 오류 되돌려 고치기 · ReAct 대체), Router 오판(단순 질문에 +1~3초), 탐색형 질문에는 맞지 않음.

도입 단계
0. 측정 — 순환이 긴 질문 유형 상위 10개
1. `PLAN_MODE=shadow` — 계획만 만들어 로그, 답은 ReAct (검사 통과율 · 계획 적절성)
2. `PLAN_MODE=on` — data · compute · report 만 + ReAct 대체
3. explore · 독립 단계 동시 실행 · 다시 계획
4. 자주 성공한 계획을 단계형 skill 로 저장 제안

정할 것: planner 모델(큰 모델 권장 — 회사판 모델 나누기와 맞추기), 회사판 `steps.py` 형식이 로컬과 같은지.
